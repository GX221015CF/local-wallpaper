# R39导入列表正确性修订

R38用户反馈查询401后计数4/61但列表空白，点击后部分行出现在底部。原性能计量和首次失败分别保留。

## 原因与修正

实际筛选入口的真实句柄复现显示，匹配项仍在模型和原生列表中，但滚动后批量逐行删除使原生顶部索引出现负值，行矩形落到客户区下方。3条自有行的最小场景在没有图片和扫描子进程时也能复现。仅在事后设置TopItem的探针遇到旧视口已无有效顶部项的异常，未作为成品。

现在仅在可见集合变化时清空并按完整模型顺序提交同一批ListViewItem。文字和图片对象继续复用，选择与滚动恢复发生在EndUpdate完成后。相同查询的后台更新保留合理顶部项，查询变化时保证选中匹配项可见。相同集合无需重新提交。

原排序沿用资源发现顺序，先新发现，再按对应记录时间倒序，最后以ID稳定区分。筛选和清空不另外按名称或图片完成时间排序。

## 验证边界

隔离测试采用正常异步入口、真实自身控件句柄、Application.Run、原生项目文本/数量/顶部索引及行矩形，并在外部点击前DrawToBitmap检查正文文字。覆盖61候选、查询早于扫描结束、图片填充、滚动中底部后401筛选、清空和快速换词、部分重查、迟到名称、筛选后实际小材料导入、关闭重开和100/125/150缩放。

这些结果覆盖控件逻辑、原生布局及离屏绘制。真实可见窗口的无额外点击呈现和输入观感仍由用户确认，实际点击触发Windows重绘的详细时序未自动操作。

## 一次体验

从桌面本地壁纸打开导入窗口，查看初始列表。向下滚动后输入401，匹配行应直接正常呈现。清空后换一个词，核对顺序、选择及右侧详情。关闭再打开，最后正常彻底退出。

读取通常为秒级。10秒仍无首批候选、列表空白/错位或提示异常时，停止后续操作并反馈首个现象。读取任务原45秒预算保持。

个人库和资源身份保护保持，R32/R34稳定性及R38后台图片优化复用。其他Windows及第三方条件沿原边界记录。
